# Supabase isolation correction

The application uses its own server-side opaque sessions, not Supabase Auth or the Data API. Migration 008 is additive. Existing account invariants, document RLS, editor code and public artwork are retained.

## Boundaries and review

- `PUBLIC`, `anon`, `authenticated`, and `service_role` lose all privileges on the eleven application tables, including column grants, the audit identity sequence and seventeen application functions. `service_role` having BYPASSRLS does not bypass ACLs. The ledger has RLS with no runtime policy and no runtime grants.
- Every application function has `search_path=pg_catalog,public,pg_temp`. Migration 008 requires the migration login to own all application tables/functions. Runtime and API roles cannot create objects in `public`; unexpected ownership or unsafe runtime/API membership aborts the migration.
- SECURITY DEFINER remains necessary for credential/session lookup, rate limiting, invitation activation, audit triggers, current-role lookup, deferred administrator enforcement and guarded soft deletion. These functions deliberately run as the table owner and bypass application RLS. They are reachable only by the trusted backend's narrow existing runtime grants (trigger-only helpers have no runtime EXECUTE). FORCE RLS would break that design and is not enabled.
- `rimdan_runtime` must be an unprivileged NOLOGIN group without parent roles. The application login must inherit only that group, own no application tables, have no schema CREATE, and have no superuser/BYPASSRLS/CREATEROLE/CREATEDB/REPLICATION rights. Requests reject unsafe credentials before resource queries. The runtime can still set `app.user_id`: possession of its password is a trusted-server compromise, not an end-user permission.
- The one-active-administrator invariant remains enforced at commit. Managers retain document read/write access; employees retain finalized-only read access. No frontend functionality is changed.

Objects stay in `public` for compatibility with existing SQL and deployments. Explicit ACLs, denied schema creation, fixed paths and disabling the unused Data API provide isolation. Moving to a private schema would require a separately reviewed migration of stored function bodies and every SQL caller. Do not add `public` or application objects to another API or publication.

Defaults are revoked globally AND in `public` for the executing migration owner, for tables, sequences and functions, from PUBLIC/API roles/runtime. Global revocation is essential for PostgreSQL's implicit PUBLIC EXECUTE. Future runtime grants must be explicit. Defaults are per creator, not per database: every future object must be created by this same owner through a reviewed migration. A new creator requires equivalent default changes before creating objects. This can affect other applications creating public objects as that owner; use a dedicated Rimdan project/database. Historical migration 001 already revokes PUBLIC access to all public tables/functions, another reason not to co-locate unrelated applications.

## Migration history and reconciliation

Use `scripts/migrate.js`, not the Supabase CLI migration ledger. This repository uses its own numbered SQL files and `public.schema_migrations`. Stop older migration runners and application traffic for the maintenance window. Disable the Data API, back up the database including roles/ACLs and the ledger, and retain the exact previously applied SQL files.

The runner reads SQL as UTF-8, hashes the actual file contents with SHA-256, takes a transaction advisory lock and exclusive ledger lock, and requires applied history to be an exact ordered prefix. It validates every applied checksum before pending SQL. All pending migrations, ledger writes and isolation verification commit together; any failure rolls back the entire pending batch. Concurrent updated runners serialize. This avoids a fresh-install window between insecure legacy functions and migration 008. Upgrades remain vulnerable until the transaction commits, so disable APIs and stop traffic first. No automatic downgrade exists.

Migrations 001–007 are unchanged. `.gitattributes` pins future SQL checkouts to LF. The runner never normalizes existing checksums or updates ledger checksums automatically. If an old checkout used CRLF, a mismatch is still a hard failure.

On mismatch: stop; do not delete ledger rows, skip checks, or blindly rehash them. Compare a protected ledger export with the exact SQL artifact actually applied and trusted repository/release copies. Restore the matching original file bytes (including line endings) and rerun. If no trusted matching artifact exists, investigate as potential tampering. A genuine historical divergence requires a documented operator reconciliation: identify every schema/data difference on a restored disposable backup, prepare and test a new forward-only corrective migration, obtain explicit review of any exceptional ledger correction, and retain before/after evidence and backups. This patch authorizes no such exceptional correction. A possibly compromised ledger cannot be made trustworthy by ACL repair alone; review accounts, sessions, grants and audit records and rotate affected credentials.

## Verification and TLS

`node scripts/verify-isolation.js --approve-production --require-api-roles` is a read-only owner check for effective privileges, RLS, function ownership/paths and owner defaults. It fails if any expected API role is absent. The migration runner runs the same check before commit (ordinary local PostgreSQL may omit the API roles). Run it after future migrations or provider changes. Maintain the explicit object manifests when adding application objects. A successful SQL check complements the dashboard check; it cannot prove the Data API toggle is off.

Remote URLs require `sslmode=verify-full`. The driver receives explicit parsed connection fields and `rejectUnauthorized:true`, calling Node's standard certificate identity verifier with the exact URL hostname, including IP addresses. Unsupported/duplicate URL options and global TLS verification disabling are rejected. Configure the provider root CA using `DATABASE_SSL_CA` PEM or URL `sslrootcert` with an encoded absolute path. Custom roots supplement Node's configured default trust so publicly signed pooler certificates remain compatible. Never solve certificate errors using `require`, `no-verify` or a disabled verifier.

For Vercel, use the custom app login on the shared transaction pooler, port 6543. The driver uses unnamed parameterized queries (no prepared-statement `name`), one checked-out client per transaction, BEGIN/COMMIT, transaction-local actor/search_path, and no persistent session state. Vercel pools are capped at one connection per instance. Migrations/bootstrap should use a direct connection or shared session pooler on port 5432. Production TLS trust, provider permissions, pool routing and Vercel deployment must still be verified manually; no real project was contacted.

References checked for this patch: [Supabase API security](https://supabase.com/docs/guides/api/securing-your-api), [connection modes and TLS](https://supabase.com/docs/guides/database/connecting-to-postgres), [node-postgres TLS](https://node-postgres.com/features/ssl).

## Local validation

Validated on 2026-11-02 using native Windows/PowerShell, Node 24.19.0, PostgreSQL 18 and headless Chromium. Tests used a new cluster bound only to 127.0.0.1:55439, randomized databases and fictional accounts; no existing environment file was loaded. Supabase-style defaults were simulated, including service_role BYPASSRLS.

- `npm.cmd test`: 19 groups, including ten backend groups and nine security groups. Coverage includes fresh installations, repeat/concurrent runners, upgrades retaining data and checksums, column-level grants, actual API-role function/ledger denials, future table/function/sequence defaults, owner operation without superuser/BYPASSRLS, atomic failure rollback, checksum/unknown-history rejection, and verifier regression detection (including PostgreSQL 17+ MAINTAIN). Separate-process CLI tests exercise migrate, isolation verification and first-Administrator bootstrap. Bootstrap refuses installations without migration 008 and verifies isolation before writing.
- Real local PostgreSQL TLS: trusted CA accepted; an untrusted self-signed certificate and wrong hostname/IP rejected. This test found and corrected node-postgres's IP-host identity fallback. No certificate check was disabled. To repeat that optional handshake group, enable TLS on a disposable local cluster with a test certificate whose SAN is `DNS:localhost` only and set `TEST_TLS_CA` to its certificate path alongside `TEST_DATABASE_URL`. Without this optional setting the handshake group is explicitly skipped; TLS configuration assertions always run.
- `tests/backend_browser.py`: passed real local sessions, invitation lifecycle, role-aware navigation, manager mark save/finalize/reopen, employee read/output restrictions and legacy import preservation.
- `tests/browser_smoke.py`, `tests/document_marks.py`, `tests/letterheads.py`: passed bilingual editing, storage/formatting, drawing/uploads/placement, original pads, twelve language/template combinations and A4/multipage PDFs. Browser harness paths now support Windows; the smoke timeout allows Windows long-document layout to complete, and all assertions remain enabled.
- `tests/mobile_ux.py`: passed seven widths in both languages, all screens, 84 template edit/save/reopen flows, drawer focus, touch drawing/placement/resize, tabs/zoom/pinch and multipage PDF parity. These are headless Chromium/CDP tests, not physical-device certification.
- `npm.cmd run build`: passed; final `public/index.html` is authenticated server mode. Temporary prototype output used for regressions was replaced by the normal build.
- JavaScript/Python syntax, all 17 PowerShell instruction blocks, and `git diff --check`: passed. Dependency audit reported zero vulnerabilities. Byte comparisons confirmed all seven historical migration files, frontend sources and original artwork are unchanged. `.env.local` and `.local` remain ignored.

The supplied directory had no Git metadata or parent repository. A local baseline commit captured the supplied non-secret files, followed by a dedicated hardening commit on `feature/supabase-security-hardening`; no remote was configured or contacted through Git. `.env.local` was neither read nor staged. Local browser artifacts, TLS test keys, test tooling and the disposable cluster live only under ignored `.local/`.

Remaining limits: local PostgreSQL is not the full managed Supabase service; real provider grants, CA chain, pool routing, Data API dashboard state and Vercel deployment remain operator checks. Objects remain in public with explicit ACLs; use a dedicated project and the documented owner for future objects. Privileged provider/owner credentials can administratively override isolation. A previously compromised ledger/account set requires investigation beyond this ACL patch. Application limitations such as MFA/recovery, retention, quotas and backup drills remain as documented in BACKEND.md. No remote migration, live bootstrap, deployment, push or merge was performed.
